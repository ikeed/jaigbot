# AIMSBot codebase evaluation — 2026-08-29

Scope: everything under `app/`, `run_app.py`, `chainlit_app.py`, `redis/`, `tests/`, `scripts/`, `.github/`, `terraform/`, `Dockerfile`, `public/`, at commit `64d2c82` (staging). ~13.9k LOC app, ~24.2k LOC tests, 875 test functions, 338 commits since 2025-09.

Method: read the core request path end to end (routes → orchestrator → handlers → services → Vertex), the Chainlit layer, memory/storage, CI and infra; ran `ruff` (0.16.5), `mypy` (1.18.2), `radon`, `vulture`, and a few AST scripts on your machine; checked two production facts from outside (`/api/config` on aimsbot.ca; Starlette 1.6 `Mount` source for lifespan propagation). Every claim below has a file reference; the things I could not verify are listed at the end.

Ranking rule for the final list: each item has a **risk** (chance of breaking something × blast radius × effort, 1–5) and a **reward** (correctness, cost, latency, maintainability, 1–5). Sorted by risk ÷ reward ascending — best bets first, big-bang refactors last. Ties broken by reward.

## 2. Verified latent bugs (the things that change your prod behaviour today)

### 2.1 `redis/` at the repo root shadows the real `redis` library
`redis/__init__.py` (188 lines, added in #181, 2026-06-08) is an in-process dict pretending to be redis-py. Python puts the script's directory first on `sys.path`, so `python run_app.py` from `/app` (the Dockerfile's `WORKDIR`/`CMD`), `python -m pytest` from the repo root, and CI's `PYTHONPATH=$GITHUB_WORKSPACE` all resolve `import redis` (`app/memory_store.py:123`) to this stub. `.dockerignore` does not exclude it. Verified on your machine: `python3 -c "import redis; print(redis.__file__)"` → `.../aimsbot/redis/__init__.py`.

Consequences: `RedisStore` "connects" (stub `ping()` returns True), `/api/config` on aimsbot.ca reports `memoryBackend: "redis"` / `appEnv: "prod"`, but sessions live in a per-instance Python dict — split across `--max-instances=2`, lost on every deploy/restart. Terraform provisions Memorystore + a VPC connector (`terraform/terraform.tfvars: enable_redis = true`) that nothing uses. `tests/unit/test_memory_store.py` doesn't notice because it injects its own fake via `sys.modules`.

Separately, `deploy.yaml:178` uses `--set-env-vars ... MEMORY_BACKEND=${MEMORY_BACKEND:-memory}` (replaces *all* env vars) while `terraform/main.tf:259` sets `MEMORY_BACKEND=redis` via a `null_resource` local-exec — two owners of the same Cloud Run env, last writer wins.

### 2.2 The classifier never gets its configured model
`app/main.py:95-97` puts `classifier_model_id` / `classifier_thinking_level` / `classifier_thinking_budget` into the vertex config. `ChatOrchestrator.__init__` never reads them, and `_handle_coaching_path` (`chat_orchestrator.py:149-158`) re-packs a dict without them. `AimsVertexConfig.from_mapping` (`aims_handler_config.py:30-31`) then falls back to `model_id` and `None`. Net: since commit `e2c102c` (2026-07-30) the classification call — the one under the 60 s budget — runs on `gemini-3.6-flash` with default thinking instead of `gemini-3.5-flash-lite`/`minimal` as `.env.example`, `deploy.yaml`, quality.yml and the docs all claim. No test asserts the classifier's model. `scripts/benchmark_classifier_models.py` constructs `ClassifierService` directly, which is why the benchmark never exposed it.

### 2.3 The "deterministic fallback" is off everywhere it's deployed
`AIMS_HEURISTIC_FALLBACK_ENABLED` defaults to `"false"` (`aims_coaching_handler.py:291-294`), is not in `.env.example` or any workflow, and `docs/aims/concern-checklist-plan.md:200` says "off in every deployed environment". On LLM timeout/failure prod returns the "classification unavailable" neutral result (`aims_turn_coordinator.py:119-140`). `CLAUDE.md:91`, `README.md:6`, `AGENTS.md` and the AIMS docs all describe `aims_engine.py` + `aims_mapping.json` as the production fallback. Your agents (and you, per our earlier conversations) are working from a mental model the code doesn't implement.

### 2.4 The Vertex client cache exists and is never used
`app/runtime.py:44 VertexClientCache` is instantiated in `main.py:18` and stored on `app.state`; no caller uses it. `VertexGateway` (`vertex_gateway.py:67,99,133,161`) and `ClassifierService._call_gemini_json` (`classifier_service.py:310`) construct a fresh `VertexClient` → fresh `genai.Client` per LLM call: new credentials (metadata-server token fetch on Cloud Run), new httpx pool (new TLS handshake), two to four times per turn (classifier, reply, endgame, feedback refinement). That is avoidable latency on every message and the `get_last_model_used()` contextvar hack in `vertex_helpers.py` exists partly because there is no shared client to ask.

### 2.5 Lifespan never runs in the shape you deploy
`run_app.py:86` mounts `app.main:app` at `/api`. Starlette's `Mount` only handles `http`/`websocket` scopes (checked in starlette 1.6.0 source), so `app/main.py:_lifespan` never executes in unified mode: `app.state.memory_store`/`vertex_client_cache` are never set and the model preflight never runs. `get_memory_store` (`main.py:38-39`) already papers over this with `getattr(..., MEMORY_STORE)` — that fallback is the tell. Low impact today (deploy also sets `VALIDATE_MODEL_ON_STARTUP=false`), but it means "startup" code in `app/main.py` is dead in production.

### 2.6 Unrelated packages in the production image
`requirements.txt` contains `booktype` (Booktype 1.5, a 2012 "FLOSS Manuals collaborative book writing tool"; its `install_requires` pulls **Django** and `simplejson` into your Cloud Run image and installs a `createbooki` script), `contextvars` (the Python 3.6 backport, a no-op on 3.13), `starlette` (transitive via FastAPI), and `types-jsonschema` (stubs). Nothing imports any of them. Dev/test deps are commented "install with `pip install .[dev]`" but no `[project.optional-dependencies]` exists. No lockfile, so the image is built from whatever PyPI serves that day.

### 2.7 Config split-brain
Twelve behaviour knobs are read with `os.getenv` outside `Settings`: `AIMS_CLASSIFY_TEMPERATURE/MAX_TOKENS/BUDGET_S`, `AIMS_ENDGAME_TEMPERATURE/MAX_TOKENS`, `AIMS_REPLY_MAX_TOKENS`, `AIMS_HEURISTIC_FALLBACK_ENABLED` (`aims_coaching_handler.py:283-294`) and the five continuation knobs at module import in `app/vertex.py:11-16`. `Settings` has copies of the five continuation knobs that drive nothing but `/config` and `/diagnostics`. In API-only mode (`uvicorn app.main:app`) `.env` is never loaded into `os.environ`, so `/config` reports one value and `vertex.py` uses another. Eleven other `Settings` fields are dead: `USE_VERTEX_REST`, `SUPPRESS_VERTEXAI_DEPRECATION`, `SAFETY_LOG_CAP`, `AIMS_CLASSIFIER_MODE`, and six `*_AVATAR_PATH/URL`.

### 2.8 Smaller but real
- `DEFAULT_CHARACTER`/`DEFAULT_SCENE` are defined twice with different text: `app/config.py:239-247` (short, used by `persona_service.py:282`) and `app/persona.py:22-37` (long, used by `chat_context.py`, `chainlit/orchestrator.py`, `routes/system.py`).
- `SessionService.prune_expired` (`session_service.py:135-183`) runs inside the request path (`chat_context.py:57-59`, whenever `int(time.time()) % 29 == 0`), iterates the whole store and does synchronous GCS uploads per expired session on the event loop. The comment says it is "usually called in the background". It isn't.
- `JailbreakGuard.LEGACY_CUES` (`security_guard.py:17-39`) matches substrings `"bypass"` and `"dev mode"` — "after your bypass surgery" triggers the jailbreak canned reply. Two cue lists exist (`security/jailbreak.py` + `security_guard.py`).
- `storage_service.py:15` shells out to `git rev-parse` at import; `.git` is dockerignored, so `GIT_HASH` is always `"unknown"` in the image. `deploy.yaml` already has `GITHUB_SHA` — pass it as a build arg.
- `http_handlers.py:93-142` logs a 1 KiB body preview of every POST at INFO by default (`LOG_REQUEST_BODY_MAX=1024`), hiding only `character`/`scene`. The clinician's `message` is logged. Your own constraint (`CLAUDE.md`: "Do not log … unredacted request payloads") is violated by default config. `patient_reply_service.py:54-64` also logs the full message on jailbreak intercept.
- `routes/system.py:164-222 /models` calls `google.auth.default()` + a synchronous `requests` session inside `async def`; `chat_orchestrator.py:402 handle_report` calls sync `storage_service.download_session` on the loop.
- `middleware.py`/`http_handlers.py` use `BaseHTTPMiddleware` and the `request._receive = receive` private-attribute hack to re-buffer bodies.
- `mypy` passes only because `implicit_optional = true` masks 14 `x: List[str] = None` defaults and bodies of untyped functions aren't checked; `--check-untyped-defs --no-implicit-optional` finds 11 real errors, `--strict` finds 280.

## 3. Structural observations by dimension

### Architecture and modularity
The intended shape — `routes → ChatOrchestrator → {AimsCoachingHandler | LegacyChatHandler} → small services` — is sound, and the `Protocol`s in `aims_dependencies.py` are a good idea. The problem is *what* flows between the pieces:

- **Two shared mutable dicts are the real interface.** `mem` (session memory) and `cls_payload` (this turn's classification) are passed through and mutated in place by `VaccineRelevanceGate.gate`, `AimsPostProcessor.post_process`, `AimsStateService.update`, `refine_fallback_feedback`, `sanitize_coaching_tips`, `metrics_service.persist`, `coach_feedback_history_service.append`, `_append_endgame_blocked_tip`, `endgame_service.check`… (`aims_coaching_handler.py:452-623`). 46 distinct string keys (`is_mirrored` ×28, `parent_concerns` ×16, `phase` ×16…) are accessed across 20+ files; some are constants in `constants.py`, most are literals. `ClassifierResult` *is* a typed Pydantic model — and it is flattened to a dict at `aims_turn_coordinator.py:111` before anyone else sees it. Zero `Enum`/`StrEnum`/`Literal` for steps, phases, roles, tones, event types.
- **Config has three representations.** `Settings` → `dict` bags in `main.py:88-133` → attributes on `ChatOrchestrator` → re-packed `dict` → `AimsVertexConfig` dataclass. The typed dataclass exists but sits at the *end* of the chain, which is how 2.2 happened.
- **The whole service graph is rebuilt per request.** `get_chat_orchestrator` (`main.py:150`) builds `ChatOrchestrator` + `SessionService` + `ChatContextBuilder`, then `_handle_coaching_path` builds `AimsCoachingHandler` + 9 services, for every `POST /chat`. Cheap in CPU, but it is why config threading is so verbose and why `self.background_tasks` ends up as mutable per-request state on a service object (`chat_orchestrator.py:45,94`).
- **Two LLM stacks.** Sync (`VertexClient.generate_text` with the 130-line auto-continue loop, `VertexGateway.generate_text*`, `vertex_call_with_fallback_text`) exists for exactly one caller — the summary narrative via `asyncio.to_thread` (`summary_service.py:156`). The async stack (used by every hot-path call) has no continuation logic. `vertex_helpers.py` has three ~90-line functions that differ by `await`; `VertexGateway` has four near-identical methods with a `try: … except TypeError: # older signature` retry that would silently re-run a request in plain-text mode if any `TypeError` occurred inside the SDK call.
- **Two classifiers.** The heuristic engine (`aims_engine.py` 535 LOC, `conversation_service.py` 799 LOC, `coaching_tip_sanitizer`/`coach_post` keyword paths, 772-leaf `lexicon` in `en.json`, `docs/aims/aims_mapping.json` imported via `docs/__init__.py`) is behind the default-off flag from 2.3. Twenty-one test files / ~8.7k test LOC exercise it. It is either a fallback (then test and document it as one) or dead weight (then delete it).
- **UI → API over loopback HTTP in one process.** `BackendClient` (`backend_client.py`) opens a new `httpx.AsyncClient` per call to `http://localhost:8080/api/...` from inside the same uvicorn worker. It keeps the API as the contract, but it doubles in-flight requests per message, runs every message through the body-logging middleware twice, and — the important part — forces `/api/*` to be unauthenticated, which it is (2.9 below).
- **Storage is a KV store used as a database.** `MemoryDataLayer.list_threads` (`chainlit_memory_data_layer.py:246-283`) calls `store.items()` twice — for a real Redis that is two full `SCAN`+`MGET` of every session of every user to render one user's sidebar. `_find_user_by_id` is a linear scan. Persona counts are read-modify-write in three places (store cache, per-session marker, GCS index) with no atomicity (`persona_service.py:208-223`, `storage_service.py:373-406`).

### 2.9 Exposure (architecture consequence, not a separate audit)
`gcloud run deploy --allow-unauthenticated` + no auth dependency on the API routers means `POST https://aimsbot.ca/api/chat` will happily spend Gemini tokens for anyone, `GET /api/config` returns project id, model ids, Redis prefixes and store size (verified from outside), and `GET /api/history?sessionId=…` returns a transcript to whoever has the id (ids are uuid4/Chainlit thread ids; thread ids appear in shareable `/chat/thread/{id}` URLs). Session ids are also accepted from the request body (`session_service.py:57`), so a leaked id is a read/write handle.

### Idiomaticness and modernity
- Router factories with closures over `settings: Any` (`routes/*.py`) instead of module-level routers + `Depends`. `settings: Any`, `logger: Any`, `memory_store: Any` throughout — 97 `Any` annotations in app code, which is why mypy is green and useless.
- 46 imports inside functions (`PLC0415`), mostly to dodge cycles (`chainlit_thread_state.py:29 from app.main import MEMORY_STORE`, `main.py:137`, `chat_orchestrator.py:145,248`, `session_service.py:139`). Cycles are a layering smell: `app.main` is imported by leaf modules.
- `logger.info(json.dumps({...}))` (15 direct sites + 15 via `telemetry.log_event`) under a text `format=` — Cloud Logging receives a text line with JSON inside it, not `jsonPayload`; severity/labels don't map; and errors are logged twice (`logger.exception(...)` then `logger.error(json.dumps(...))`, e.g. `http_handlers.py:79-86`, `chat_orchestrator.py:364-370`).
- `print()` for startup diagnostics (`run_app.py`, `utils/env.py`), `time.time()` for latency instead of `perf_counter`, `a != a` for NaN (`coach_post.py:414,420`), `chat_timeout = self.timeout if self.timeout != 15.0 else 120.0` (`backend_client.py:106`).
- Typing style is split: 33 files import `List/Dict/Optional`, 193 sites use `X | None`. `requires-python = ">=3.13"` makes the old style pure noise. `build-backend = "setuptools.backends._legacy:_Backend"` is a private module path.
- `Dockerfile`: root user, no lockfile, no multi-stage, `pip install` at build from a floating `requirements.txt`.
- CI: `tests.yml` and `quality.yml` both trigger on PRs into `staging` and both run the full suite (2× minutes); `quality.yml` embeds a 100-line Python script in bash in YAML that recomputes `RANGE` because the bash variable isn't exported; two "Dump OIDC claims (debugging)" steps live in the production deploy and terraform workflows; action pins are mixed (`checkout@v7`, `@v6.0.3`, `@v6`); secrets are passed as plain `--set-env-vars` rather than `--set-secrets`.

### Simplicity and clarity
- 137 `except Exception` in app code — one per ~100 lines. Many wrap operations that cannot fail (`response_payload["sessionId"] = ctx.session_id` inside try/except at `chat_orchestrator.py:183-187`; `logger.error(end_event)` inside try/except with a fallback `logger.info` at `http_handlers.py:216-225`; `telemetry/events.py:56-71` is three nested try/excepts around `logger.info`). The dangerous ones swallow logic errors: `AimsStateService.update` (`aims_state_service.py:135-136`) catches everything, so a bug in the concern state machine silently yields a turn with stale state and the session continues corrupted.
- Duplication: `_handle_coaching_path`/`_handle_legacy_path` are ~80% identical; request-id extraction exists three times (`http_handlers.get_request_id`, `ChatOrchestrator._get_request_id`, `AimsCoachingHandler.handle._req_id`); the "classification unavailable" and deterministic fallback results are built in both `AimsTurnCoordinator.run` and `ClassifierService.classify_turn` with slightly different shapes; `AimsPromptBuilder` is 69 lines of static methods that forward to `app.prompts.aims` unchanged.
- Function size: `AimsCoachingHandler.handle` 322 lines; `AimsEndgameService.check` 202 lines / CC 56; `ClassifierService.classify_turn` CC 44; `aims_engine.classify_step` CC 41; `chat_context.ChatContextBuilder.build` CC 23. Radon MI: `conversation_service.py` 5.9, `aims_state_service.py` 8.9 (both "C").
- Comment rot: "This module is extracted as part of Phase 1 … In subsequent commits, the logic will be moved verbatim" (`security/jailbreak.py:1-11`); "They are currently not yet wired into app.main" (`conversation_service.py:8-9`, it is wired); "Actually, let's just use PATH_CHAT consistently … was a bit fuzzy" (`backend_client.py:116-119`); `APP_TITLE = "AIMSBot (Gemini Enterprise)"` (`constants.py:14`); docs still say Python 3.11 and `admin`/`admin` (code requires `AUTH_PASSWORD`, `chainlit_app.py:163-166`).
- The **why** comments in the AIMS logic (`aims_coaching_handler.py:164-217`, `storage_service.py:35-47`) are the best part of the codebase. Keep that habit; delete the archaeology.

### Generality
- `locales/en.json` is 42 KB: UI strings, API error strings, LLM prompt fragments (`patient_reply.retry_prompt` etc.) and 772 heuristic keyword leaves under `lexicon`. Translating the file would change classification behaviour; `message()` returns the *key* on a miss, so a typo ships silently as user-visible text.
- Runtime data imported from documentation: `app/aims_mapping_loader.py:8 from docs.aims import aims_mapping`, requiring `docs/__init__.py`, `docs/aims/__init__.py` and negation rules in `.dockerignore`.
- Deployment specifics in code: bucket defaults in `config.py:71-72`, `aimsbot.ca` in `deploy.yaml`, `cr-vertex-runtime@` SA name, `DEFAULT_REGION = "us-west4"` vs `validate_region` fallback `"us-central1"`.
- Prompt templates render with `str.format` (`prompts/loader.py:24`); every literal brace in a prompt must be doubled (`classify_turn.txt` already has 7 `{{`), and a future JSON example in a prompt is one un-escaped brace away from a `KeyError` at request time.
- Chainlit UI is 1.7k lines of vanilla JS that patches Chainlit's React DOM (`message-roles.js`, `splash.js`) with a hand-bumped `?v=20260809-session-lock` cache key in two files.

### Tests
Strong in volume and in the regression/transcript approach. Weak spots: the autouse `MockVertexClient` (`tests/conftest.py:48-109`) picks its response by substring-matching the *prompt text* ("unified", "classify", "aims framework", "parent persona", "day going") and contains a special case for one named test — prompt copy edits can silently reroute the whole suite; `clean_app_state` manages `app.state.aims_mapping`, which only `summary_service` still uses; 33 test files import `app.main` (booting logging, the store, `google.auth.default()`), 168 calls to private `_methods`, 18 `sys.modules` patches, session fixture deletes `app.aims_engine` from `sys.modules`. `test_memory_store.py` fakes redis itself, which is exactly why 2.1 was never caught.
